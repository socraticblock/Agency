## Open items carried into the baseline (not fixed here)

1. **Git-ignored untracked content is invisible to the scope audit** — a new out-of-scope file under a
   `.gitignore`d directory or `core.excludesFile` pattern yields `PASS`. A verifier can therefore leave a live
   module in the delivered tree at PASS time. Compensating review step:
   `git status --ignored` / `git clean -ndX`. Disclosed in prose (`SKILL.md`, `CHANGES-V3.5.3-DEV-REVIEW9.md`),
   not in the gate output.
2. **Intermittent false refusal (`gate.raw-budget-unmeasured`)** — a same-size edit made inside git's stat
   window is invisible to `git status`/`git diff` while the raw inventory sees it, so a legitimate in-scope
   refactor is refused with a request for a baseline `--budget-note`. Reproduced 1 run in 6. Fail-safe
   direction, but it makes `tests_pe_preflight.py` non-deterministic.
3. **Documentation defects** — `SKILL.md` states the gate suite has 48 cases (50) and that the validator
   imports PyYAML (it imports only stdlib); `CHANGES-V3.5.3-DEV-REVIEW11.md` states 9 new tests (11 ships) and a
   "documented" `--out` migration that is not written; `evals/ARM_TREATMENT_PROTOCOL.md` names
   `grade_candidate.py`, which ships nowhere; `validate_skill.py` does not validate cross-directory
   `evals/…` routes; the .11 "no real coding-agent run" disclaimer reads globally over the shipped n=1 pilot
   results. Deliberately not patched here, so the frozen bytes stay traceable to the reviewed archive.

## Post-freeze amendment — 2026-10-16 (front-matter description only)

After the freeze was recorded, the front-matter `description:` on `SKILL.md` line 3 was reworded from the
behaviour statement (`Engineering judgment and verification for reliable, maintainable coding-agent changes.`) to
the trigger-first form `Use when writing, fixing, testing or reviewing code.`

- **Why:** each session's system prompt carries only each skill's name + description and loads the body on
  demand, so the description *is* the loading trigger. The previous wording was a capability statement with no
  `Use when …` condition, so a code task raised inside a non-coding session could miss the load entirely.
- **Why that exact length (52 chars):** the prompt skill index renders at most 57 characters plus `...`
  (`agent/skill_utils.py:828` `SKILL_PROMPT_DESC_LIMIT = 60`; `extract_skill_description` at `:837-840` truncates
  only when the description exceeds 60), and the fleet's static auditor (`capability-engineering/scripts/audit_skill.py`)
  reviews that same 57-character window. A 60-character draft carrying a trailing `Verify.` rendered whole in the
  runtime but the auditor flagged the window as a mid-word cut (`…code. Veri`) — any wording past character 57 is
  invisible where the load decision is made, so the description was cut to the complete trigger sentence, which
  ends at 52.
- **Scope:** metadata only. No commitment, gate, evaluator, reference or body prose was altered; the reviewed
  archive remains the byte-source for all doctrine content above this section.
- **Label unchanged (`3.5.3-frozen.1`)** deliberately: `scripts/validate_skill.py:91-99` requires the front-matter
  `version:` and `INDEX.md`'s `**Version:**` line to agree, and in-flight evaluation artifacts cite the frozen
  label. A label bump would drag `INDEX.md` and the arm-treatment references in behind it for a description-only
  edit.
- **Re-verified after the edit:** `scripts/validate_skill.py` → VALID (100 files); description 52 chars against the
  validator's 240 limit, not truncated for the prompt, and the auditor's 57-character routing window now clears
  (the mid-word warning is gone). Doctrine bytes are otherwise untouched, so the remainder of this file's
  provenance claims and its open items still stand.
